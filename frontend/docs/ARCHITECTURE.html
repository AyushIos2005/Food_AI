3 · Authentication & roles

Session

  • JWT signed with JWT_KEY, delivered as an httpOnly cookie named token
  • Never read by client JavaScript — no XSS token theft
  • Logout blacklists the token in Mongo, so it can't be replayed
  • verifyToken re-reads the user each request, so role changes apply instantly

Role guards

  • verifyToken — any signed-in account
  • verifyAdmin — chef only (food upload / delete / chef list)
  • verifyUser — user only (complaints)
  • requireRole(...) — generic multi-role helper

OTP flow

  • 6-digit code, stored SHA-256 hashed
  • Compared with timingSafeEqual
  • 10-minute lifetime, 60-second resend cooldown
  • Used for signup verification and password reset

5 · Real-time notification path

User A likes User B's post │ ▼ blog.controller.like_post │ ▼ notification.service.createNotification({ recipient: B, sender: A, type: "LIKE" }) │ ├──▶ Notification.create(...) persisted first — survives socket failure │ └──▶ io.to("user:B").emit("notification:new", doc) │ ▼ NotificationContext (frontend) │ ├─▶ prepend to list ├─▶ unreadCount + 1 → red badge on the bell └─▶ toast popup
Socket authentication: the handshake carries the same token cookie. The server verifies it, checks the blacklist, re-reads the user, then joins the socket to room user:<id>. A client-supplied user id is never trusted.

6 · Soft-delete & undo (AI history)

DELETE /api/ai-service/amze/history/:id recipe ──copy──▶ deletedAIsolution isDeleted = true, deletedAt = now (row stays in the collection; queries filter isDeleted: false) PATCH /api/ai-service/amze/history/:id/undo deletedAIsolution ──restore──▶ recipe isDeleted = false, deletedAt = null, restoredAt = now

Both AI collections share this pattern, so a single history screen can delete and restore across amzeFood and createNewFood without knowing which one an item came from — each record is tagged with historyType on the way out.

7 · Defence in depth

Transport

  • helmet headers
  • CORS allow-list from CLIENT_URL
  • trust proxy for real client IPs

Input

  • Request sanitisation
  • zod schemas on body/params/query
  • Body size capped by BODY_LIMIT

Abuse

  • Global apiLimiter
  • Per-flow limiters for login, register, OTP, reset
  • Separate AI and upload limiters

Secrets

  • bcrypt 12 rounds for passwords
  • SHA-256 + constant-time compare for OTPs
  • Env validated at boot — fail fast

Two env vars, one origin: CLIENT_URL governs REST CORS and FRONTEND_URL governs Socket.IO CORS. Set both to your frontend origin or live notifications will silently fail while the rest of the app works.
